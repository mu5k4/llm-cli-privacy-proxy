# Decisions

## Recorded Decisions
- The privacy runtime is treated as the core product, while Codex CLI, Claude Code, and future clients are separate integrations.
- Client-specific authentication and config instructions belong in docs/integrations rather than in the core runtime documentation.
- The stack is designed to remain client-agnostic so additional integrations can be added without renaming the runtime.
- Shareable handoff artifacts should exclude local runtime state such as .env and privacy cache data.
- The August 25, 2026 audit remediation cycle is now the main implementation driver for the next project improvement pass.
- Phase 1 must prioritize the two high-severity confidentiality issues before medium- and low-severity hardening work.
- The outbound request path must move from partial pass-through forwarding to explicit allowlisted schema construction.
- The nested `/responses` request schema will stay intentionally narrow and fail-closed during Phase 1 instead of trying to safely support the full upstream tool/schema surface immediately.
- Cross-slot detection will use a canonical concatenated logical text stream with offset-based mapping back into the original slots.
- Placeholder restoration must become protocol-aware and limited to approved passive human-visible text fields only.
- Protocol-aware restoration will restore only approved assistant text/refusal fields in SSE and non-stream response objects, and will not restore placeholders inside tool arguments, code, reasoning, IDs, or other active protocol fields.
- Phase 2 local endpoint authentication will use a per-install random secret embedded in the local provider path rather than a separate user-facing auth prompt or a transport change away from the current local HTTP flow.
- Codex config mutation will use top-level TOML block-aware edits plus parser-backed validation instead of regex section rewrites, and the script will write UTF-8 without BOM so the resulting config reparses cleanly after atomic replacement.
- The next implementation step after Phase 2 is Phase 3 Item 6, starting with bounded request/session/cache controls in the existing runtime rather than jumping ahead to later overlap or supply-chain items.
- Phase 3 Item 6 will be implemented with fail-closed request size/depth/text budgets, short queue waits instead of unbounded backlog, TTL- and byte-bounded session state, LRU-bounded Presidio cache persistence, and container-level CPU/memory/PID/read-only limits before moving on to session-ownership hardening.
- The analyzer cannot run under the same 1 GB cap as the lightweight proxy in this environment on August 31, 2026; keep the proxy at 1 GB while raising the analyzer to 3 GB and preserving tighter limits through read-only root, tmpfs for transient control files, and a workspace-backed model cache mount.
- Phase 3 Item 9 uses two layers of local authorization: the install-generated secret route still gates access to the local service, and each reusable protect/restore session now has its own server-generated high-entropy session secret that must accompany reuse, restore, and delete requests.
- Phase 3 Item 11 invalidates stale Presidio negative-cache entries by folding a security-relevant runtime fingerprint into each cache key; the current fingerprint covers app version, analyzer config, request-text budget, and chunking parameters, with `PRESIDIO_CACHE_FINGERPRINT` available as an override if future deployments need to inject a broader external version stamp.
- Phase 4 Item 8 preserves confidentiality by merging every connected overlap set to the union of its covered character range, while still choosing the placeholder label from the highest-priority contributing detector span.
- Phase 4 Item 10 uses an explicit supported boundary-visibility window for chunked Presidio scans: entities crossing a 4,000-character chunk split are supported only when the uninterrupted cross-boundary segment stays within the configured overlap window, and larger cross-boundary segments now fail closed instead of being silently under-scanned.
- Phase 5 Item 7 keeps the analyzer fully offline at runtime by baking the pinned GLiNER snapshot locally, copying the pinned `microsoft/mdeberta-v3-base` tokenizer/config files into that same directory, and rewriting the bundled `gliner_config.json` so GLiNER resolves both tokenizer and encoder config from the local pinned path instead of the network.
- Deferred runtime validation confirmed on August 31, 2026 that supported long cross-boundary entities should still pass through the bounded chunking path, so uncached Presidio chunk scans must be serialized within a request under the current one-slot scanner semaphore instead of competing with each other and self-failing with `429`.
- Deferred runtime validation confirmed on August 31, 2026 that the current overlap-union logic behaves correctly against the pinned live detectors: when Presidio and Nosey Parker produce nested or partially overlapping spans, replacement boundaries should remain the full union of the connected sensitive range while the chosen placeholder label can still come from the highest-priority contributing span.
- Deferred runtime validation confirmed on August 31, 2026 that the proxy's restore surface remains intentionally narrow at the boundary it controls: only passive assistant-visible text/refusal fields are restored, while active protocol fields such as tool arguments, reasoning text, encrypted reasoning content, and identifiers remain placeholderized. External client approval and execution behavior still cannot be proven from this repository alone.
- Deferred runtime validation confirmed on August 31, 2026 that the pinned proxy's supported request surface is narrower than some broader Responses client conventions: for example, `stream_options` currently supports only `include_obfuscation`, so compatibility claims should be limited to the enumerated allowlist unless a future sanitized live client capture shows otherwise.
- Deferred runtime validation resolved the audit inventory discrepancy on August 31, 2026: the authoritative audited snapshot inventory is the 31 concrete paths in `scan.scan.scope.artifactsReviewed`, while five additional aggregate rollup entries in that same list explain the larger apparent count and prior 27/29 references are summary-text inconsistencies rather than evidence of missing reviewed source files.
- Local bind-host verification on August 31, 2026 confirmed that the deployment remains loopback-bound as assumed by the audit severity notes: source defaults, current `.env`, and live Docker port bindings all keep the proxy on `127.0.0.1` rather than a wider host interface.
- The audit artifacts and temporary remediation-planning file were useful during remediation, but once the cycle completed they became historical records rather than active planning inputs and could be removed from the shareable branch state.
- The long-term Python dependency layout should use a root `pyproject.toml` as the declared source of truth plus hash-locked install artifacts per runtime environment, rather than duplicate handwritten `requirements.txt` manifests alongside lockfiles.
